# Why This Benchmark Exists

DeepSWE made one lesson feel concrete to me: the hard part of evaluation is not making a model answer a prompt. The hard part is deciding what should count as a task, what should count as a pass, how to tell whether the task was already leaked into the world, and how to preserve enough evidence that another engineer can debug the score without trusting your taste.

`benchmark-euterpea` is my small attempt to practice that discipline in a domain where I can audit the ground truth myself. I chose music theory first, not because Datacurve or model evaluation is about music, but because music theory has a rare combination of compact prompts and strict symbolic correctness. `F#` and `F` are not interchangeable. `Fx` and `G` can name the same sounding pitch while being different answers in tonal spelling. A model that writes a correct paragraph can still fail an output-only task. These are the same kinds of contract boundaries that matter in coding agents and data pipelines, just expressed in a domain small enough to inspect by hand.

The repo is intentionally modest. It runs local Ollama models against original tasks, stores raw JSON artifacts, grades them with deterministic verifiers, and publishes curated summaries through a static hiscore page. The important part is the shape: task proposal, contamination note, verifier, run provenance, failure reason, public report, and failure corpus. That loop is what turns a domain expert's intuition into model behavior someone else can evaluate.

I also wanted the project to make its weaknesses visible. The current tasks are not a final benchmark suite. They are a controlled first domain, plus agent-compliance tasks and early Haskell/Euterpea-style stubs that point toward richer symbolic solver work. The docs call out contamination risk, verifier quality, provenance, and failure-corpus promotion because those are not side notes; they are the benchmark.

For a hiring reader, the reason to care is not that I built a music quiz. The reason to care is that I can take an ambiguous evaluation problem and turn it into runnable infrastructure: a harness, strict grading, raw artifacts, reports, issue-driven task intake, and a technical narrative that explains why a failure matters. That is the same muscle needed to build reliable coding-data systems, researcher tools, and benchmark pipelines where plausibility is not enough.
